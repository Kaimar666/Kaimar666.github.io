## 2. 调研结论与本站设计判断

首轮研究了 12 个真实个人站，包括中文生活 / 技术记录与英文作者 / 作品集网站；11 个实际首页进行了桌面首屏观察，另一个因验证页只研究正文结构。第二轮新增 kage-ai，查看了其英文和中文首页的正文与桌面首屏。未对参考站进行移动端、无障碍或性能审计。首轮详情见参考调研，新增站点见 [kage-ai 补充调研](research/kage-ai-followup-2026-10-10.md)。

当前优先参考用户明确喜欢的三个网站（设计建议；借鉴特征不等同复制完整栏目）：

- [Anthony Fu](https://antfu.me/)：个人简介串联文章、项目、兴趣与外部入口；可用轻量项目标识增强辨识度。
- [pseudoyu](https://www.pseudoyu.com/)：独立创作、项目与生活兴趣共同构成个人身份，中文记录自然承载日常表达。
- [kage-ai 英文首页](https://kage-ai.com/)和[中文首页](https://kage-ai.com/zh/)：清楚的姓名 / 头像 / 定位，分组展示代表成果，并给每类成果相应的阅读、体验或站外入口。用户已选择中文页的深色简介区 + 浅色内容区这一视觉组织方式；不等同复制全部栏目。

首轮其他参考作为辅助：

- [Steph Ango](https://stephango.com/)：暖色留白、文字列表、阅读舒适度。
- [Anthony Fu](https://antfu.me/) 与 [Paco Coursey](https://paco.me/)：短个人介绍自然连接文章、项目和其他入口。
- [pseudoyu](https://www.pseudoyu.com/posts) 与 [Limboy](https://limboy.me/)：生活、思考、项目过程可以共存；短记录也是完整内容。
- [Tania Rascia](https://www.taniarascia.com/)：内容多了以后，以主题、连续系列和人工精选合集辅助阅读。
- [Maggie Appleton](https://maggieappleton.com/garden-history)：允许笔记持续生长，不要求每次发布都写成完整长文。

本站建议：首页帮助陌生人认识“你是谁、关注什么、做过什么”；记录区承载持续表达；精选内容帮助第一次来访的人开始阅读。生活与项目共享同一个人的叙事，项目也要有容易找到的独立入口。

“简洁美观”的候选表达：清爽的个人工作室气质，稳定字体层级、充分但适度的留白、一个克制的强调色、轻分隔线、中文可读性，以及清楚的身份介绍。头像、照片、原创标记可以增强辨识度。

## 3. 三个候选视觉方向

| 方向 | 页面组织 | 气质与侧重点 | 取舍 |
|---|---|---|---|
| 温润书页 | 顶部轻导航；介绍与近况；文字记录和精选项目双栏 | 温暖、安静，表达与项目相对平衡 | 项目视觉冲击较弱，可在详情页补截图 |
| 个人工作室 | 左侧个人介绍与外部入口；右侧项目预览，接文字列表 | 清爽、利落，作品更显眼 | 需要真实项目素材；避免职业标签压过生活表达 |
| 生活札记 | 短介绍与近况；带日期的生活 / 想法 / 项目动态；侧栏主题与入口 | 自然、亲近，更新门槛低 | 需用精选项目 / 代表作补足长期辨识度，避免完全由近期动态决定形象 |

**当前设计基准：** 个人工作室风格，深色顶部个人介绍 + 浅色内容区，精选项目与最近记录并列。参考 Anthony Fu、pseudoyu、kage-ai 的个人介绍与内容组织。以第三轮预览中的“作品与记录并列”作为后续基准；首轮温润书页及固定侧栏的工作室探索稿不再作为默认。颜色细值、真实文案、头像、模块数量和近况细节继续讨论。

### 第二轮细化建议（尚未确认为最终布局）

1. **顶部：** 姓名 / 个人标识 + 简短导航。候选：首页、记录、项目、关于。
2. **首屏：** 头像、姓名 / 昵称、一句话定位、2–4 句自然介绍，以及少量代表项目或真实平台入口。介绍同时体现生活关注与创作，不预设用户是程序员、AI 专家或课程作者。
3. **精选项目：** 2–4 个代表项目，附名称、简短说明、状态和体验 / 相关文章 / 源码等实际链接；项目可以是工具、非代码作品或小实验。是否使用截图卡片仍待定。
4. **最近记录：** 3–5 条文章、短想法或生活片段，以清楚的标题与轻量日期组织；主题和形式在二级列表中逐步扩展。
5. **近况与其他入口：** 可选近况小块，以及带用途说明的站外入口。不强制把所有外部链接塞进顶部。

**已确认明暗分区：** 深色个人简介区 + 浅色内容区。细化稿暂采用深蓝紫、近白内容背景和少量暖橙点缀；色值、强调色、头像处理、介绍高度仍为设计建议。全页深色或全页浅色不再作为当前默认。

kage-ai 的 Research、Books、Courses、Concepts 来自作者实际内容，不自动成为本站栏目。双语、订阅和商业入口也不是因参考站存在就默认实施的需求。其 Concepts 的稳定主题地址可作为以后专题页的参考。

## 4. 当前导航方案与首页内容

**当前首期导航方案：** 首页 / 记录 / 项目 / 关于。用户明确选择生活与想法统一归入“记录”（C13）；其余入口按这一已提出的方案继续整理，显示名称与顺序应可通过配置调整。外部入口可以在简介或页尾；更多栏目有内容之后再出现。

| 入口或模块 | 用途 | 建议首期内容 |
|---|---|---|
| 首页 | 简短身份介绍、开始阅读与看项目的入口 | 姓名 / 昵称、1–2 句定位、代表记录、最近记录、1–3 个精选项目、其他入口 |
| 记录 | 统一承载生活、想法和其他主题的正文入口 | 建议长文与短想法；按主题标签整理，具体内容形式和图片记录待定 |
| 项目 | 呈现创作成果及过程 | 名称、简介、状态、可选截图、体验 / 源码 / 关联文章链接 |
| 关于 | 了解本人及联系 | 自我介绍、长期关注、公开联系方式与真实平台链接 |
| 近况（可选） | 让读者知道当前关注 | 首页一小块；是否另设 `/now` 页面待定 |

不要为了填满页面强制准备所有模块。没有项目时不出现空卡片；记录少时可显示简介与一篇代表记录；没有好封面的文章应仍然排版完整。图片是否作为首页视觉核心需由真实素材决定。

### 记录入口的组织建议

- 默认以最近发布的内容列表作为入口，生活、想法、阅读、技术等是可增补的主题，不要求互斥。
- 每条正文保留独立稳定地址；标签改变不导致原文搬家。首页“最近记录”从统一记录集合生成。
- 专栏 / 连续系列有内容后再创建，在记录内提供入口；不自动占用顶部导航。以后可将常用专栏提升为导航入口。
- 标签与专栏支持配置名称、简介、显示顺序和隐藏状态；创建和维护方式要写进 Markdown 编辑说明。
- 是否在首期界面同时展示形式筛选、主题筛选或搜索，按内容数量决定，避免在少量记录阶段展示过多控件。这些是实施建议，不是新增的用户已确认功能。

[Now 页的原始说明](https://nownownow.com/about)强调当前人生重点。本项目可以借用这一信息形式，但不据此承诺营销效果，也不把它当每日打卡要求。

## 5. 分类与专栏：先保留能力，后确定名称

建议分开以下四种关系，不把它们混成同一棵目录树：

| 维度 | 它回答的问题 | 候选例子 | 修改方式目标 |
|---|---|---|---|
| 内容形式 | 这是怎样的一份内容？ | 文章、短想法、图片记录 | 添加内容时指定；新展示形式可能需要开发 |
| 主题标签 | 内容谈什么？ | 生活、阅读、设计、技术 | 可随时增补或整理；一条记录可有多个标签 |
| 专栏 / 系列 | 是否属于有延续性的内容？ | 月记、读书笔记、某项目日志 | 先写内容，确定持续性后再创建；不要求每条记录都归属专栏 |
| 精选合集 | 想带读者怎样读？ | 初次来访、值得回看的几篇、关于创造 | 可手动排序；允许跨主题和跨形式选入内容 |

例如，“散步时想到的一个产品设计”可以是一篇文章，同时属于生活和设计两个主题，又被选入某个精选合集；正文仍只有一个稳定地址。将来添加“旅行”主题，只改内容元数据和标签资料，不必重做页面。

“数字花园”是组织和更新内容的思路，首期可只采用持续修订与关联文章；知识图谱、双向链接和成熟度标签均是以后候选，不默认为必做。参考：[Maggie 对数字花园的说明](https://maggieappleton.com/garden-history)。

## 6. Markdown 更新方式与扩展边界

用户已选择本地 Markdown。建议后续做到：

1. 文章正文和短记录用 Markdown；标题、日期、标签、专栏、摘要等用文件头元数据。
2. 项目、导航、首页模块和其他入口通过可读的配置 / 内容文件维护，常规更新无需改页面代码。
3. 标签、专栏、精选合集支持新增、改名、隐藏、排序；使用稳定标识，显示名称与网址标识分开。
4. 首页精选与最新分开：精选可手动选定；最新按日期生成。模块的开关、顺序及显示数量可配置。
5. 内容支持草稿与本地预览；发布前可检查中文排版、图片和链接。保存历史版本，能够找回误改内容。
6. 修改分类时不改变原文地址；确需改地址时提供重定向。媒体文件有稳定组织规则，迁移时可导出正文与素材。
7. 提供易懂的编辑说明：新增文章、添加项目、更改导航、创建专栏、替换头像、发布与回退各有范例。

**弹性边界：** 新增标签、既有形式的内容、链接或专栏应属于文件编辑；引入全新交互、内容形式、第三方数据同步或大幅改布局，仍可能需要开发。不要承诺所有未来变化都无需代码。

实施前可以评估适合内容网站的静态生成方案，但本轮不锁定技术栈。[Astro 内容集合文档](https://docs.astro.build/en/guides/content-collections/)证明本地 Markdown、内容集合和元数据校验是可行路线，是否选用仍取决于最终页面与发布要求。

补充研究（不作为当前采用方案）：[Decap CMS](https://decapcms.org/docs/intro/)可给 Git 中的内容加编辑界面；[Ghost](https://ghost.org/help/tags/)有标签管理与自动标签集合。若未来改用后台，可以再讨论；用户当前明确选择 Markdown，不据此增设后台。

### 部署讨论记录（2026-10-10）

用户新增问题：是否需要自己租公网服务器，是否可以用 GitHub Pages 的 github.io 地址。已核实候选方案见 [部署调研](research/deployment-options-2026-10-10.md)。

- 当前内容型网站可以预先生成静态网页，由托管平台公开提供访问；用户无需自己租用和维护服务器。Markdown 修改后触发重新构建，不影响持续更新能力。
- 源码 / Markdown 所在仓库、实际网站托管平台、对外域名是三层独立选择。仓库可以在 GitHub，网页托管在 GitHub Pages 或 Cloudflare。
- GitHub Pages 可使用 `<GitHub用户名>.github.io` 的个人站地址，也可绑定自定义域名；显示品牌 Kaimar 不要求 GitHub 用户名同名。[官方说明](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)。GitHub Free 的 Pages 面向公开仓库；私有仓库 Pages 需要相应付费计划。如果草稿提交到公开仓库，即使不生成网页，仓库中的原文仍可被查看。
- Cloudflare Pages 仍有静态站托管能力，但官方现在建议新项目使用 Workers。新的 Cloudflare 候选以 Workers Static Assets 为主，不把旧 Pages 教程作为默认。[Cloudflare 当前方向](https://developers.cloudflare.com/pages/)、[静态资源计费与限制](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/)。
- 对本站拟采用的纯静态输出，Cloudflare 静态资源请求免费且不限请求次数；构建和文件有各自限额。动态 Worker 请求是另一种计费与限额，不能笼统宣称所有功能永久免费。
- **费用补充（用户询问，2026-10-10）：** Cloudflare 静态托管可以使用免费方案；Workers Builds Free 每月 3,000 构建分钟，Cloudflare Pages Free 每月 500 次构建。自有域名的注册与续费和托管费用分开计算。此次仅澄清费用，不把提问理解为用户已经取消 GitHub Pages 优先选择。[Workers 构建额度](https://developers.cloudflare.com/workers/ci-cd/builds/limits-and-pricing/)、[Pages 免费额度](https://developers.cloudflare.com/pages/platform/limits/)。
- 两个平台都应使用实际发布地址验证国内与海外访问。未作跨地区网络测量，不仅凭“全球 CDN”宣称国内更快或稳定。
