# Kaimar 个人网站：首期实施范围

日期：2026-10-10（Asia/Shanghai）  
状态：本地实现与验证已完成，详细结果见 [完成记录](implementation-status.md)；尚未切换线上站点。  
已确认设计和需求以 [设计确认记录](personal-website-design-brief.md) 为准。

## 1. 已定基准

- 品牌名称统一为 **Kaimar**。
- 身份标签：**Agent 工程师 · 运动员**。
- 简介保留用户原句：**一个在大厂工作的攻城狮，但是内心实际上是一个运动员，哈哈哈哈**。
- 个人工作室风格，深色介绍区 + 浅色内容区，桌面端作品与记录并列，手机端顺序堆叠。
- 生活与想法统一归入“记录”，主题标签和专栏可以持续调整。
- 内容通过本地 Markdown 文件编辑，再发布。
- 用户明确表示项目与站外入口后续补充，首期可以不依赖这些资料。
- 访客预计覆盖国内与海外；实际部署地址需要进行对应网络的访问验证。
- 用户愿意公开源码与 Markdown 仓库，首期优先采用 GitHub Pages。

## 2. 首期页面与行为

| 页面 | 首期内容与行为 |
|---|---|
| 首页 | Kaimar 的介绍和字母头像；按已发布内容生成精选项目、最近记录；可配置关注方向与其他入口 |
| 记录 | 统一的内容列表；长文和短记录共用内容系统；按日期组织，支持主题与专栏入口 |
| 记录正文 | 标题、日期、可选摘要、标签、Markdown 正文、图片与相关链接；长文有目录时显示目录 |
| 项目 | 项目列表与详情；名称、说明、状态、可选截图、体验 / 源码 / 相关记录链接 |
| 关于 | 已确认的姓名、身份与简介；后续可补个人故事、兴趣和公开联系方式 |

导航暂按 **首页 / 记录 / 项目 / 关于**，名称、顺序与显示状态都通过文件配置。

## 3. 内容尚未补充时

- 正式首页只展示真实、已发布的内容。预览中的“拾光”等示意项目和示意文章不转为真实作品。
- 没有已发布项目时，首页精选项目模块自动隐藏；没有记录时，最近记录模块自动隐藏。两者都有内容时采用已确认的双栏布局；只有一个模块有内容时合理利用可用宽度。
- 项目和记录页保留可访问的页面，并采用简洁的空状态，不展示假的内容或统计数字。
- 没有真实账号 / 邮箱 / 其他网页地址时，相应站外入口隐藏；配置后再出现。
- 暂用 K. 字母头像，头像可通过配置替换。
- 没有真实近况时，可以使用已提出的“这里关注”内容，或关闭该模块；不把演示的小工具进展当成本人的近况。
- 为编辑提供的样例内容均作为草稿或模板保留，不公开。

## 4. 用户可以通过文件维护什么

| 维护项 | 文件编辑目标 |
|---|---|
| 个人信息 | 名称、身份标签、简介、头像、关注方向 |
| 记录 | 新增 / 编辑 Markdown，长文与短记录，标题、日期、摘要、标签、专栏、图片 |
| 项目 | 新增 / 编辑项目介绍，修改状态、截图、外部链接和关联文章 |
| 分类与专栏 | 创建、改名、调整说明与排序，隐藏不需要展示的项目 |
| 首页 | 选择精选内容，调整显示条数、模块开关及站外入口 |
| 导航与主题 | 调整导航名称、顺序、显示状态，以及常用颜色配置 |

主题分类改变不应使正文地址变化。专栏的显示名称与稳定标识分开；需要改正文地址时提供重定向方式。常规内容更新不要求改页面组件。

## 5. 编辑与发布路径

首期交付一条完整的本地工作流程：

1. 从记录 / 项目模板复制一个 Markdown 文件。
2. 填写标题、日期、标签和正文，放入图片。
3. 在本地预览草稿、文章排版、图片和链接。
4. 修改发布状态，使内容进入正式列表与首页模块。
5. 构建可发布的站点文件。

配套编辑说明应覆盖：写第一篇记录、添加项目、创建主题和专栏、添加站外入口、替换头像、预览与构建、找回误改内容。

本阶段先交付本地可运行、可编辑、可构建的版本，并准备 GitHub Pages 自动构建发布配置。托管已选 GitHub Pages；先按平台域名衔接，独立域名可后续绑定。

### 已选部署路线：公开 GitHub 仓库 + GitHub Pages

首期按可迁移的静态站构建。用户已明确接受公开仓库并优先选择 GitHub Pages，Cloudflare 保留为以后可能迁移的备选。

- **GitHub Pages：** 官方支持静态网页和自定义域名，个人站默认地址为 `<用户名>.github.io`。GitHub Free 下使用公开仓库。[GitHub 官方说明](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)。
- **Cloudflare Workers Static Assets：** 采用 Git 构建或上传静态输出，适合把源码仓库与公开网站分开。Cloudflare 目前推荐新项目使用 Workers；纯静态资源存储没有额外费用，静态资源请求免费且不限次数，文件与构建有具体限额。[当前产品建议](https://developers.cloudflare.com/pages/)、[静态资源计费](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/)。
- **独立域名：** 可后续绑定；域名不与 GitHub 用户名绑定。尚未核实可注册性，也未发生购买。

只读核实到当前连接账号为 **Kaimar666**，已经存在公开仓库 [Kaimar666/Kaimar666.github.io](https://github.com/Kaimar666/Kaimar666.github.io)，默认分支为 `master`。该个人站对应地址为 `https://kaimar666.github.io/`；不需要新注册一个名为 Kaimar 的账号。当前没有创建远程仓库、提交变更或部署。

#### 既有博客衔接建议

1. 正式开发前读取现有仓库的 Git 历史和文件，保留旧输出的可恢复快照。
2. 在本地或开发分支构建新站，保留现有默认分支历史；不用强制推送或清空远程仓库完成换站。
3. 首页已核实有一篇 2021-01-06 的旧文章“使用hugo在window下搭建个人博客”，旧地址为 `/post/blog/`。先保全原文与旧页面，迁移后保留旧路径或提供兼容页；迁移细节以实际旧文件为准。
4. 新版本本地确认后，再接入现有仓库、确认 Pages 当前发布源，并安排新的 Actions 构建 / 发布方式。原站未成功经网页检索工具打开，该结果不能代表已验证线上是否可用。
5. 若采用个人站根地址，Astro `site` 使用实际 `github.io` URL，不添加普通项目站的仓库名前缀；站点 URL 可配置，适应以后绑定独立域名。

#### 公开仓库下的草稿编辑规则

未准备公开的草稿建议放在本地忽略目录，预览工具可以按需读取但不进入公开仓库。`draft` 字段控制是否生成公开网页，不能隐藏已提交到公开仓库的源文件。提供编辑说明与有意义的检查，帮助用户区分“本地私人草稿”和“可公开的发布 / 模板内容”。

## 6. 技术路线建议

建议采用 **Astro + 本地 Markdown 内容集合 + TypeScript + 原生 CSS**，用于以内容和阅读为主、少量交互的站点。主要目的是把内容与页面展示分开，保留独立文件和未来迁移的空间。此路线为实施建议，不是用户已经指定的技术栈。

[Astro 官方内容集合文档](https://docs.astro.build/en/guides/content-collections/)支持本地 Markdown 内容集合与元数据校验，可用于记录、项目和相关内容关系。具体依赖版本在正式实施时确认，使用依赖锁文件。用户没有要求可视化后台，首期更新路径以 Markdown 为核心。

第一版视觉沿用已选预览的深蓝紫介绍区、近白内容背景和少量暖橙点缀；这些作为初始配置，后续可修改。正式页面使用适合中文与英文混排的字体，保持克制的动画和清楚的焦点状态。

## 7. 验收点

- 桌面和手机都能读清简介、导航、文章与项目内容，布局无横向溢出。
- 首页只出现真实已发布内容；零内容、仅有记录、仅有项目和两者都有内容时均有合理布局。
- 草稿不进入公开列表；长文、短记录、标签、专栏与精选关系按内容文件生成。
- 按编辑说明新增一篇记录、一个项目、一条外部入口，能够在本地预览并构建，且不修改页面代码。
- 调整分类不改变正文地址；缺失的可选封面、链接和摘要不会破坏排版。
- 导航和核心操作可用键盘访问；标题层级、链接标签和图片替代文本清楚。
- 页面有正确的标题、描述、作者信息与可分享的基础元信息，能适应后续确定的正式域名。
- 公开发布前，在实际候选地址验证国内与海外访问；不把托管品牌宣传当作实际网络测量。
- 构建检查通过，浏览器没有由页面代码引发的明显错误，生产输出不包含示意内容。
- 旧博客内容与 Git 历史可恢复；旧文章路径有迁移或兼容方案；公开仓库的草稿维护方式与编辑说明一致。
